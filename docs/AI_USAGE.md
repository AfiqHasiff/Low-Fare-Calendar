# AI Usage — Low Fare Calendar

This document reflects honestly on how AI tooling was used during the design and implementation of this assessment. It covers what was used, where it helped, where it failed, and what that means for AI as a development tool.

---

## Tools Used

**Claude Code (Anthropic)** was the sole AI tool used throughout this project — for design sessions, code generation, validation, documentation, and codebase exploration.

---

## Where AI Was Used

### 1. Brainstorming and Design Sessions

The author proposed architectural directions and used Claude Code as a sounding board to evaluate trade-offs across three approaches: Cache-Aside, Write-Through + Singleflight, and full CQRS. The AI reasoned through trade-offs, and helped structure the decision — but every architecture decision was made by the author.

**One exchange illustrates why this distinction matters.** During the TTL design discussion, the AI was under the impression that hot routes should be given a *longer* TTL — reasoning that more traffic justifies keeping data cached longer. This is conceptually backwards. Hot routes are high-demand flights that sell out faster; their prices change more frequently and go stale more quickly. They need a *shorter* TTL and more frequent warmer runs, not longer ones.

This is the clearest example in this project of why AI cannot be the sole decision-maker on architecture. A correct proposal requires domain knowledge — in this case, understanding how flight inventory behaves — that the AI did not have and could not derive from the problem statement alone.

### 2. Test Writing

AI was used to generate test scaffolding: Testcontainers setup, MockMvc test structure, and assertion patterns. The generated scaffolding was reviewed and adjusted by the author to ensure coverage of the right edge cases — particularly around cache miss / hit / stale paths and partial provider failure scenarios.

### 3. Code Boilerplate Generation

Repetitive structural code was generated by AI following the author's specifications: Spring Boot configuration classes, constructor injection wiring, `@Component` / `@Service` annotations, and `application.yml` property binding classes. This is low-risk, high-volume work that AI handles well.

### 4. Code Validation

Before committing implementation code, AI was used to review it for correctness issues — specifically around concurrency primitives. Two areas required careful scrutiny:

- **`putIfAbsent` vs `computeIfAbsent` under Virtual Threads** — `computeIfAbsent` does not guarantee that only one thread executes the mapping function under concurrent load; `putIfAbsent` + an explicit `CompletableFuture` is the correct singleflight primitive in Java.
- **Lua script atomicity for Redis lock release** — the lock release script must check ownership and delete atomically; a non-atomic implementation creates a race window where a thread can delete a lock it no longer owns.

The `computeIfAbsent` issue is worth noting: it was not caught during the initial design brainstorm — it required the author to specifically prompt for an adversarial correctness review. AI did not volunteer it unprompted.

### 5. Documentation Generation

AI generated the content of `docs/SYSTEM_OVERVIEW.md`: sequence diagrams, component reference descriptions, green/red path analysis. The author provided the architecture and reviewed all generated content for factual correctness before accepting it.

---

## Where AI Was NOT Used — Architectural Decisions

AI did not make architectural decisions. The brainstorming sessions had AI present reasoned through options and trade-offs provided by the author. The author ultimately decided the approach and owned the final design. The TTL inversion example above is the clearest evidence that blindly following AI proposals would have produced a functionally incorrect system — one that keeps stale prices in cache longest for exactly the routes where accuracy matters most.

---

## Assessment of AI as a Development Tool

AI accelerated this project significantly. Design sessions that would normally span multiple days of async written proposals and review cycles were compressed to focused sessions of a few hours. Boilerplate generation eliminated hours of mechanical typing. Codebase exploration across a large Go monorepo — which would normally require either prior deep knowledge or a slow manual search — was fast and targeted.

But the project also produced two clear categories of AI failure that required human intervention:

1. **Conceptually wrong proposals** — the TTL inversion was not a syntax error or a missed edge case. It was a proposal that was logically coherent on the surface but wrong because it lacked the domain understanding that hot inventory sells out faster. No amount of prompting precision would have caught this without the author knowing how flight inventory behaves.

2. **Missed correctness issues requiring targeted prompting** — the `computeIfAbsent` deadlock risk under Virtual Threads was not surfaced during general review; it required the author to specifically ask for an adversarial concurrency audit. AI in a confirmatory posture will miss things that AI in an adversarial posture catches.

AI is a force multiplier when the human using it has the domain expertise to direct it, evaluate its proposals critically, and know which questions to ask. It is not a substitute for that expertise, and treating its output as authoritative — particularly on architecture — would produce systems that are wrong in ways that are plausible-looking and hard to debug later.
